# Q1 findings: busy-desktop confirm in `setup-workspace.sh`

## Plasma OSD over D-Bus

- plasmashell exports `/org/kde/osdService` on service `org.kde.plasmashell`,
  interface `org.kde.osdService`. Checked against the installed Plasma 6.7
  `plasmashell` binary (its embedded introspection data lists `showText` and
  `hide` next to the `osdText`/`osdProgress` signals).
- Text message: `showText(QString icon, QString text)`, e.g.
  `qdbus6 org.kde.plasmashell /org/kde/osdService org.kde.osdService.showText preferences-desktop-virtual "Desktop not empty. Tap D again to set up here."`
- The OSD hides itself after its own timeout; the script never calls `hide`.
  So the message's display time is Plasma's, not `CONFIRM_TIMEOUT_MS`. T3's
  daemon may want to call `hide` when the request expires.
- The script tries `qdbus6`, then `gdbus`, then logs and continues. Without
  plasmashell (nested test session) the first press still arms and exits 0.

## Pending-request state

- File: `${XDG_RUNTIME_DIR:-${TMPDIR:-/tmp}}/setup-workspace-<uid>.pending`,
  content `<epoch ms> <x11 desktop number>`, plus a `.lock` file beside it.
- The read/decide/write runs under `flock`, so overlapping presses are
  serialized and only one can consume a pending request. The lock fd is
  closed before launching Konsole, so children never hold it.
- A request counts only if it is at most 2000 ms old, for the same desktop
  and not in the future; anything else (old, other desktop, garbage, clock
  jump) is overwritten. No cleanup step is needed; `XDG_RUNTIME_DIR` is
  cleared at logout anyway.
- Consequence: presses alternate arm/confirm. Tap, tap gives one setup; four
  quick taps give two setups (arm, confirm, arm, confirm), because after a
  confirm the desktop is busy and the next press arms again.
- The emptiness check now reports `empty` / `busy <n>` through
  `output_result` and treats a failing `kdotool` call as a hard error, so a
  broken check cannot show the confirm prompt.

## Testing

- The nested KWin session could not be started inside the Claude Code
  sandbox: `dbus-run-session` fails with "Failed to open socket: Operation
  not permitted" (unix socket creation is blocked). The sandbox was not
  disabled.
- Instead: `bash -n`, plus a dry run with stubbed `kdotool`, `konsole`,
  `qdbus6` and `gdbus` on `PATH` (stubs simulate window lists, launches and a
  present or missing OSD). All cases passed: empty desktop unchanged; busy
  first press arms, shows the OSD and launches nothing; second press within
  2 s launches 3 and places only the new windows; press after 2.2 s shows the
  message again; other desktop starts over; missing OSD logged, exit 0;
  stale, garbage, empty and future state files ignored; concurrent presses
  give exactly one setup per arm; `XDG_RUNTIME_DIR` unset falls back to
  `$TMPDIR`; failing `kdotool` exits 1 without arming.
- Not verified here: the real OSD, real KWin window counting, and the real
  Ctrl+Meta+D shortcut. These need the user's live session.

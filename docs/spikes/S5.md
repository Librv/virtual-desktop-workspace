# S5: bare daemon (no Qt GUI in vdwd)

Branch `spike/bare-daemon`. Question: can vdwd idle at the footprint of a
QtCore + QtDBus process (about 14 MB RSS, 1.3 MB private) instead of a Qt GUI
process (about 47 MB RSS), without changing behavior?

## Baseline (nested session, 2026-10-17)

| Process | RSS | Private |
|---|---|---|
| vdwd on main, idle | 49 MB | 7 MB |
| vdwd on main, after menus | 77 MB | 13 MB |
| QGuiApplication + KGlobalAccel, nothing else | 47 MB | 6.6 MB |
| QCoreApplication + QtDBus, nothing else | 13.7 MB | 1.3 MB |
| `vdw-menu-demo` start to menu shown (software renderer) | 65 ms | |

vdwd idle is at the floor of a Qt GUI process, so only removing QtGui from the
daemon helps.

## Design

Two executables:

- **vdwd**: `QCoreApplication`, links only Qt Core/DBus, KF6 ConfigCore,
  CoreAddons and Service. No QtGui, no KF6 DBusAddons, GuiAddons,
  GlobalAccel or KIOGui (all pull in libQt6Gui).
- **vdw-ui**: short-lived helper with all GUI work: radial menu, toast,
  modifier tracking (`KModifierKeyInfo`) and app launching
  (`KIO::ApplicationLauncherJob`, so the systemd scope, activation token and
  Exec field codes stay KIO's job). Software scene graph renderer.

### Helper lifetime

vdwd starts one `vdw-ui` when something needs it and keeps it while any of
these hold: the gesture machine is not Idle, a toast is visible, launches are
pending. When none hold, vdwd sends `quit`. vdw-ui also exits on stdin EOF so
it never outlives a crashed daemon. A main-shortcut press starts the helper
right away, so it is up before the 250 ms hold threshold (start takes about
65 ms) and tracks modifiers for the whole gesture, including the "busy reply
after modifiers were released" case (AwaitingOpenResult).

vdwd finds the helper next to its own binary
(`QCoreApplication::applicationDirPath() + "/vdw-ui"`).

### Protocol

One line per message over the helper's stdin/stdout, UTF-8, fields separated
by a single space, the last field may be JSON (no newlines inside).

vdwd to vdw-ui:

- `mods <mask>`: track these modifiers (Qt::KeyboardModifier bits of the main
  shortcut's first chord). The helper answers `mods 1` or `mods 0` 150 ms
  later (the Wayland key state is not ready at start) and on every change.
  Mask 0 always reads as held. vdwd assumes held at a main press, so the
  delay never cancels a confirm.
- `menu <x> <y> <json items [{id,name,icon}]>`: show the menu centered at x,y
  (x = -1: screen center).
- `hidemenu`
- `select`: answer `selected <id>` or `selected -` for the current pointer.
- `toast <json {icon,text,chord}>` and `hidetoast`. `text` may contain `{mods}`
  and `{key}`; the helper fills them from `chord` (Qt key|modifier int of the
  first chord, 0 for none: `{mods}` empty, `{key}` "the shortcut"). A workspace
  name containing a literal placeholder would be replaced too (accepted).
- `launch <n> <json {app,args}>`: launch one app (KService desktop name plus
  extra args, as `Launcher::launch` does today). Answers `launched <n> <pid>`
  or `failed <n> <json error string>`.
- `quit`

vdw-ui to vdwd: `ready` once at start, and the replies above.

### Shortcuts without KGlobalAccel

Raw D-Bus to `org.kde.kglobalaccel` `/kglobalaccel` `org.kde.KGlobalAccel`:
`doRegister(as)`, `setShortcutKeys(as, a(ai), u) -> a(ai)`,
`shortcutKeys(as) -> a(ai)`, `unregister(s, s)`. Key sequences are `(ai)`
(Qt key|modifier ints, from QtCore). Flags as used by the KGlobalAccel
client library: SetPresent = 2, NoAutoloading = 4, IsDefault = 8 (verified in
the nested session: default = IsDefault|NoAutoloading = 12, then current =
SetPresent = 2, both with the same action id and keys; a user change made with
`setForeignShortcutKeys` survives a vdwd restart; `setShortcutKeys` with 2 does
not override stored keys). vdwd re-registers when `org.kde.kglobalaccel`
reappears (QDBusServiceWatcher). Presses arrive as `globalShortcutPressed` /
`globalShortcutReleased (s component, s action, x timestamp)` on
`/component/vdw`, interface `org.kde.kglobalaccel.Component`.
`ShortcutKeys` works on ints; the toast text that names keys is built by
vdw-ui (`QKeySequence` is QtGui).

## Findings

It works. `readelf -d build/dev/bin/vdwd` lists only Qt6Core, Qt6DBus,
KF6Service, KF6ConfigCore and KF6CoreAddons. Unit tests and the nested
integration test (including real key events through kglobalaccel) pass.

Nested session, menu held and released 10 times:

| | main (software renderer) | bare daemon |
|---|---|---|
| vdwd idle | 49 MB RSS, 7 MB private | 18 MB RSS, 1.6 MB private |
| vdwd while menu held | 93 MB RSS, 30 MB private | 19 MB RSS, 1.6 MB private |
| vdwd after 10 menus | 77 MB RSS, 13 MB private | 19 MB RSS, 1.7 MB private |
| vdw-ui while menu held | | 94 MB RSS, 30 MB private |
| vdw-ui after release | | not running |

Costs: one helper start (about 65 ms) per gesture and per launch, the
helper's 65 ms is hidden behind the 250 ms hold threshold; one more
executable and a line protocol to keep in sync. The kglobalacceld restart
path (re-register) is untested.

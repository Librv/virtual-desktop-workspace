# S2 findings: radial overlay on LayerShellQt

Date: 2026-10-17. KWin 6.7.5, layer-shell-qt 6.7.5, Qt 6.12, KF6 6.31.
Prototype: `spikes/S2/` (throwaway). All runs below were in the nested
headless KWin (`VDW_DEV_DIR=/run/user/1000/vdw-s2 scripts/dev-session.sh`),
never on the live session. The nested session was stopped afterwards.

## Summary

| # | Question | Answer | Status |
|---|---|---|---|
| 1 | Pointer motion on a full-screen overlay surface with keyboard interactivity `none`? | Yes. Enter and motion events arrive, the window never becomes active. | verified nested (fake pointer) |
| 2 | Pointer position at open? | Use `workspace.cursorPos` from a KWin script (arrives 12 ms after the script is loaded). Fallback: first `enter`/motion event. `QCursor::pos()` not usable. | verified nested; live check needed |
| 3 | Does the shortcut release still reach kglobalaccel while the overlay is up? | Yes, with keyboard interactivity `none` and also with `exclusive`. | verified nested (fake keyboard into KWin); live check needed |
| 4 | Keep alive and hidden, or create on demand? | Keep alive: about 13 ms from show to first frame vs about 65 ms when creating (nested, software rendering). Either is fine; creating on demand is simpler and still under 100 ms. | measured nested |
| 5 | Kirigami theme colors in light and dark? | Rendered correctly with Breeze Light (default) and Breeze Dark (scheme copied into the nested `kdeglobals`). Live theme switching not tested. | verified nested; live check needed |

## What was built

- `spikes/S2/radialmath.{h,cpp}`: pure `RadialMath::sliceAt(center, pointer,
  count, deadZoneRadius)`, `angleFromUp`, `sliceCenterAngle`. Slice 0 is
  centered straight up, slices go clockwise, intervals are half-open (a
  pointer exactly on a boundary belongs to the next slice clockwise), `-1` for
  no slices or inside the dead zone (distance <= radius).
- `spikes/S2/radialmathtest.cpp`: Qt Test, 6 angle rows, 21 `sliceAt` rows
  (dead zone edge, far away, boundaries, 1/3/4/6 slices, count 0 and negative)
  and a total/round-trip test for 1..12 slices. `ctest` passes.
- `spikes/S2/main.cpp` + `Overlay.qml`: `QQuickView` with
  `LayerShellQt::Window` (overlay layer, anchored to all four edges,
  exclusive zone -1, scope `vdw-s2-radial`, transparent), QML drawing with
  `Shape`/`PathAngleArc` slices, `Kirigami.Icon`, `Kirigami.Theme` colors, a
  center dead zone with a cancel icon, and the "No workspaces yet" empty
  state. A `MouseArea` with `hoverEnabled` feeds pointer events to a C++
  `Menu` object, which calls `RadialMath::sliceAt`.
- Triggers: D-Bus (`org.kde.vdw.S2Spike` `/S2`: `Show`, `Release`, `Cancel`,
  `Hide`, `Status`, `Quit`), stdin lines, and an optional real global
  shortcut (`--shortcut Ctrl+Meta+F9`: press, hold threshold, show, release
  prints the selection). Output lines are prefixed `S2 `.
- Options: `--kbd none|exclusive|ondemand`, `--mode keep|create`,
  `--center enter|kwin|qcursor`, `--layer overlay|top`, `--slices`,
  `--dead-zone`, `--debug-overlay`, `--verbose`.
- Test helpers for the nested session only: `tools/fakeinput.c`
  (`org_kde_kwin_fake_input` client, pointer and keyboard), `tools/shot.cpp`
  (ScreenShot2 `CaptureArea`), `nested-authorize.sh` (writes the two
  authorizing `.desktop` files into the nested `XDG_DATA_HOME`),
  `list-windows.js` (KWin script listing the stacking order).

## Build and run

```
cmake -S spikes/S2 -B spikes/S2/build -G Ninja
cmake --build spikes/S2/build
ctest --test-dir spikes/S2/build --output-on-failure
```

Needs `LayerShellQt`, `KF6GlobalAccel`, Qt6 Quick/DBus, `wayland-client` and
`wayland-scanner` (all installed here). The CMake file only uses the system
Wayland protocol XML it ships itself (`tools/fake-input.xml`, a minimal copy
because `plasma-wayland-protocols` is not installed).

## Nested-session test rig (reusable for S1 and later tests)

1. Authorize helpers: `VDW_DEV_DIR=... spikes/S2/nested-authorize.sh spikes/S2/build`
   then `VDW_DEV_DIR=... scripts/dev-session.sh run -- kbuildsycoca6`
   (ScreenShot2 only recognizes the helper after the service cache is rebuilt;
   fake-input worked without it).
2. Fake input (works): `scripts/dev-session.sh run -- spikes/S2/build/s2-fakeinput
   abs 1100 300 key 29 down sleep 200 key 29 up` (evdev codes). KWin offers the
   global at version 6, the helper binds 4. This injects only into the nested
   KWin, since it connects to the nested `WAYLAND_DISPLAY`.
3. Screenshot (works): `scripts/dev-session.sh run -- env QT_QPA_PLATFORM=offscreen
   spikes/S2/build/s2-shot out.png [X Y W H]`. The virtual backend renders
   and `ScreenShot2.CaptureArea` returns a 1920x1080 ARGB32 image, with
   alpha 0 where the overlay is transparent (verified: pixel (300,800) is
   0,0,0,0 with the menu open, and the wallpaper-less empty session is also
   all zero).

Gotchas hit: the first `s2-shot` hung because the pipe's write end stayed open
inside the D-Bus message (fixed by scoping the message); JS numbers passed by a
KWin script's `callDBus` arrive as int32 (`ii`), not double, so a slot taking
`double` is "No such method" (the prototype has both overloads).

## Q1: pointer motion with keyboard interactivity none

Observed (`--kbd none`, 5 slices, fake pointer moves in the nested KWin):

```
S2 show() returned after 0 ms
S2 first frame swapped 22 ms after Show, window 1920x1080 at 0,0
S2 pointer enter 700,400 after 8583 ms
S2 center 700,400 from first pointer event (enter) after 8583 ms
S2 pointer move 1100,300 after 8783 ms
S2 highlight 1 Web
S2 pointer move 1200,700 after 8984 ms
S2 highlight 2 Files
S2 pointer move 700,800 after 9184 ms
S2 highlight 3 Mail
```

`Status` after show: `active=0`, so the overlay never took keyboard focus.
KWin script listing (stacking order, `list-windows.js`):

```
s2win[0] resourceClass=s2-radial ... layer=9 normalWindow=true dock=false
  skipTaskbar=true skipSwitcher=true wantsInput=false active=false
  geometry=0,0 1920x1080
s2active none
```

`--layer top` reports `layer=3`, `--layer overlay` reports `layer=9`, so the
surface really lands on a different (higher) KWin layer for overlay. The
surface covers the whole output at 0,0 1920x1080.

Esc handling: with `none` the surface receives no key events (fake Esc while
the overlay was up produced no `key event` line). With `exclusive` the overlay
got Esc (`key=0x1000000`), at the cost of taking keyboard focus
(`overlay window active=1`). So Esc cannot be handled in the overlay without
taking the keyboard. See the recommendation.

Things to note for later tasks:

- `normalWindow=true` for the layer-shell surface (and `windowType=0`). The
  KWin script that decides "is this desktop empty" (S3/T3) must not count
  windows whose class is vdwd's own, or any `layer`-shell surface, or the
  open menu would make every desktop look busy. Filter by `resourceClass` or
  by `skipTaskbar && skipSwitcher`; a layer-shell specific property was not
  found in the script API.
- `acceptsFocus` is `undefined` in the script API for this window.

## Q2: pointer position at open

Options measured, all with the pointer at a known position before `Show`:

| Source | Result |
|---|---|
| First `wl_pointer.enter`/motion on the surface | Works, but with a stationary pointer **no enter event arrives** after the surface maps: `no pointer event 500 ms after show` (reproduced twice, nested). The first event only comes when the pointer moves. So this alone cannot center the menu on a pointer that rests while the key is held. |
| KWin script reading `workspace.cursorPos` | Works: `kwin workspace.cursorPos = 1100,250 after 64 ms` with `Show` at 0 and the script loaded at 52 ms (create mode); 13 ms after Show in keep mode. The script calls back into the app over D-Bus (`callDBus`). |
| `QCursor::pos()` | Not usable on Wayland (Qt has no global pointer position; returns the last position seen by Qt). Option `--center qcursor` exists in the prototype but was not exercised. |

Coordinates: `workspace.cursorPos` and the surface-local pointer coordinates
agree because the overlay is at 0,0 and covers the output (single monitor,
scale 1). With a fractional scale `cursorPos` is in logical (device
independent) coordinates, same as Qt's, but this was not tested.

Recommendation: ask KWin for `workspace.cursorPos` when the menu opens
(load the small script once at daemon start and invoke it per show, or have
the vdwd KWin script from S3 expose a D-Bus method or push the cursor
position with the "show menu" request), use the first enter/motion event only
as a fallback. Note the script round trip is asynchronous: show the surface
(or start its fade-in) only after the position arrives, which took 12 ms.
Alternatively the vdwd KWin script can read `cursorPos` and call
`ShowMenu(x, y)` on the daemon directly, which merges Q2 with S3's script.

## Q3: does the release reach kglobalaccel while the overlay is up

Tested in the nested session without any real input device: the prototype
registered `Ctrl+Meta+F9` through `KGlobalAccel` (kglobalacceld lives inside
KWin, see T0b), and `s2-fakeinput` sent keyboard events (`29` ctrl, `125`
meta, `67` F9) into the nested KWin. Sequence: modifiers and F9 down, 600 ms,
pointer move, 200 ms, F9 up, modifiers up.

```
S2 shortcut PRESSED
S2 hold threshold reached, showing menu       (250 ms later)
S2 show() returned after 0 ms
S2 kwin workspace.cursorPos = 900,500 after 13 ms
S2 pointer enter 900,500 after 14 ms
S2 pointer move 1000,350 after 362 ms
S2 highlight 0 3 Konsoles
S2 shortcut RELEASED after 800 ms
S2 SELECTED 0 3 Konsoles
S2 hidden
```

The same sequence with `--kbd exclusive` (overlay window active, keyboard
focus held by the overlay) gave the same `RELEASED` and `SELECTED` lines. So
`globalShortcutActiveChanged(false)` still fires with the overlay mapped,
for both interactivity modes, because KWin handles global shortcuts before
dispatching keys to clients.

This also shows that KGlobalAccel press and release are testable in the
nested session through `org_kde_kwin_fake_input` keyboard events, contrary to
the T0b expectation that the nested session cannot produce key events. That
is useful for S1 and for integration tests of the gesture state machine.

Caveats: this used F9 with modifiers on KWin's virtual backend, not the live
keyboard path (libinput, key repeat, modifier-only state). The user should
confirm on the live session (step list below). The prototype removes its
shortcut registration on exit (`removeAllShortcuts`), so nothing was left in
the nested `kglobalshortcutsrc`; nothing was registered on the live session.

## Q4: show and hide latency

Measured in the nested session (virtual backend, software rendering, so
treat as an upper bound for a GPU session):

| Mode | Show to first frame swapped |
|---|---|
| keep (create at start, hide/show) | 13 ms on every show after the first (22 ms on the very first) |
| create on demand (new `QQuickView` each time) | 51 to 54 ms to create and `show()`, first frame 64 to 67 ms after Show |

Both are fine for a menu that appears 250 ms after the key goes down. Keeping
the view alive costs a mapped-but-hidden QML scene (memory) and means the
`wl_surface` state is reused; creating on demand costs about 50 ms and makes
the surface get a fresh `enter` event and fresh screen, which avoids stale
state (e.g. the active screen when multi-monitor lands). Unverified: show
latency on the real GPU session, and whether hidden-then-shown surfaces
repeat the "no enter on stationary pointer" behavior identically live.

## Q5: Kirigami theme colors, light and dark

Screenshots (alpha channel flattened to white by the viewer, so the gaps
between slices look white; the real output is transparent there):

- `docs/spikes/S2/nested-light.png`: Breeze Light, selected slice
  `Kirigami.Theme.highlightColor` with highlighted text, others
  `backgroundColor` at 92% alpha.
- `docs/spikes/S2/nested-dark.png`: Breeze Dark (the scheme file copied into
  the nested `kdeglobals`, nested home only). Background, text and highlight
  switch correctly; icons come from the nested default icon theme.
- Empty state, dark: dark rounded box, light text "No workspaces yet".

Notes: `Kirigami.Theme.inherit: false` with `colorSet: Window` is set on the
root item; `Kirigami.Icon` and `Kirigami.Units` work in a plain `QQuickView`
(no `QQmlApplicationEngine` or Kirigami app needed, only `QGuiApplication`).
A QML gotcha: an `Item` has a read-only `data` property, so a delegate must
not declare `property var data`. Not tested: switching the theme while the
daemon runs (the QML colors are bindings, so they should follow the
`KColorScheme` change signal, but this must be seen live), non-Breeze
schemes, accent colors, high-DPI.

## Live-session steps for the user

Do these in a normal Plasma session (not the agent's nested one). The
prototype registers a throwaway global shortcut and removes it on exit.

1. Build:
   ```
   cd <repo>
   cmake -S spikes/S2 -B spikes/S2/build -G Ninja
   cmake --build spikes/S2/build
   ctest --test-dir spikes/S2/build --output-on-failure
   ```
   Expect `100% tests passed` for `radialmathtest`.
2. Run with a global shortcut that does not clash (F9 is only an example):
   ```
   spikes/S2/build/s2-radial --shortcut Ctrl+Meta+F9 --center kwin --debug-overlay
   ```
   It prints `global shortcut Meta+Ctrl+F9 registered: 1`. If it prints 0
   or the shortcut never fires, pick another combination.
3. Click into some other window (a terminal or a text editor), so there is a
   focused window.
4. Hold Ctrl+Meta+F9 for more than 250 ms. Expect the menu centered on the
   pointer, with the red debug frame around the whole screen.
5. Move the mouse around without clicking. Expect the slice in the pointer's
   direction to highlight, the center circle (dead zone) to show the cancel
   icon, and the terminal output to print `highlight N name`. The window you
   clicked in must keep its focused look (title bar active) while the menu is
   up; if its title bar goes inactive, interactivity stole focus.
6. Release over a slice. Expect `S2 shortcut RELEASED ...`, `S2 SELECTED N
   name`, and the menu to vanish. Repeat releasing in the center
   (`CANCELLED (dead zone)`).
7. Tap the shortcut quickly: expect `TAP (released before hold threshold)`
   and no menu.
8. Hold the shortcut with the pointer still: the menu should still center on
   the pointer (that is the `workspace.cursorPos` path). Compare with
   `--center enter`: the menu should wait until you move the mouse.
9. Press Esc while the menu is up: with the default `--kbd none`, nothing
   should happen (expected, see findings); try `--kbd exclusive` to see Esc
   cancel (and note that the focused window loses focus during it).
10. Open with the pointer near each screen edge and corner: the menu is
    clipped by the screen, which tells how much T4 needs to shift the center
    (the spec says centered on the pointer; decide whether to clamp).
11. Theme: run once, switch System Settings, Colors between Breeze Light and
    Breeze Dark (and an accent color), then open the menu again (restart the
    app if the colors do not change live) and check legibility and contrast
    of text, highlight and the cancel icon.
12. Hold the shortcut over a panel, a fullscreen video or game window and a
    window using the pointer lock, and tell which of them the menu fails to
    cover or breaks.
13. Press Ctrl+C in the terminal to exit; it prints `global shortcut removed`.
    Check System Settings, Shortcuts has no leftover "vdw-s2-spike" entry
    (remove it there if present).
14. Compare modes: `--mode create` and `--mode keep` (default); say whether
    either feels slower.

## Recommendation for T4

1. Use LayerShellQt overlay layer, anchors on all four edges, exclusive
   zone -1, `KeyboardInteractivityNone`, `QQuickView` (or `QQuickWindow`)
   with transparent clear color, and `Kirigami.Theme` in a plain QML scene.
   This works as prototyped (hover events, no focus theft, transparent,
   themed).
2. Get the center from KWin, not from the surface: the vdwd KWin script (S3)
   reports `workspace.cursorPos` together with the "hold reached" request, or
   the daemon loads a one-shot script like `Menu::askKWinForCursor` (about 12
   ms). Use the first `enter` event as fallback only. Show or fade in the
   menu after the position is known. Pass whole numbers as `int` (or accept
   both int and double slots) in `callDBus` targets.
3. Release handling: rely on `KGlobalAccel::globalShortcutActiveChanged(false)`
   as the "select now" event. It still arrives with the overlay mapped.
   Selection = `RadialMath::sliceAt` on the last pointer position at release.
4. Esc: with `none` the overlay cannot see keys. Options: (a) accept the
   keyboard (`exclusive`) for the duration of the menu, losing focus on the
   current window (Esc then also works in the overlay; the release still
   arrives); (b) keep focus untouched and use the center dead zone plus
   releasing outside as the cancel (the spec already cancels on center
   release); (c) register a temporary global Esc shortcut through
   KGlobalAccel while the menu is open (steals Esc system-wide during the
   hold, only for a moment). Prefer (c) if it works live, else (a). This is a
   design decision for the user; the SPEC currently promises Esc cancels.
5. Keep the surface and its QML scene alive (hidden) or create on demand:
   both are fast enough (13 ms vs about 65 ms nested). Start with create on
   demand per show for simplicity and fresh screen state; switch to keep if
   the user feels latency.
6. Make the selection math exactly the spike's `radialmath.{h,cpp}` and its
   tests (half-open sectors, dead zone inclusive). Slice 0 straight up,
   clockwise.
7. The "is the desktop empty" check in T3 must ignore the overlay window
   (class `vdwd` or the like): layer-shell surfaces show up as
   `normalWindow=true` while the menu is up. A pick happens after the menu
   closes, but a tap-confirm race with a still-mapped surface is possible, so
   hide the menu before the emptiness query.
8. T4 test strategy: the pure math in Qt Test; an integration test in the
   nested session can drive the whole gesture with `s2-fakeinput` and
   `KGlobalAccel` as done here (hold, move, release) and check the output
   plus a screenshot, since the nested session does support fake input and
   ScreenShot2 once the two helper `.desktop` files are authorized.

## Proposed ARCHITECTURE/DECISIONS changes

ARCHITECTURE.md, Radial menu section, replace the open questions with:

> QML scene in a full-screen transparent LayerShellQt surface on the overlay
> layer (keyboard interactivity none), owned by the daemon. The menu center
> is `workspace.cursorPos` obtained from the KWin script (Wayland has no
> global pointer position for clients; the surface gets no `enter` for a
> resting pointer). Selection is computed from the pointer angle relative to
> the center (pure function, unit-tested). The shortcut release still
> reaches kglobalaccel while the overlay is up (S2), so the gesture state
> machine's release event is the "select" trigger. Esc handling is an open
> choice (see S2).

ARCHITECTURE.md, Testing: the nested session can produce key and pointer
events through `org_kde_kwin_fake_input` (a helper executable authorized via a
`.desktop` file with `X-KDE-Wayland-Interfaces=org_kde_kwin_fake_input` in the
nested `XDG_DATA_HOME`) and screenshots through ScreenShot2 (`.desktop` with
`X-KDE-DBUS-Restricted-Interfaces=org.kde.KWin.ScreenShot2`, then
`kbuildsycoca6`), so shortcut press/release and the overlay are testable
there. This corrects the T0b assumption.

DECISIONS.md, candidate entries (need the user's decision on the Esc one):

| # | Decision | Why |
|---|---|---|
| next | Radial menu overlay uses keyboard interactivity none and takes its center from KWin `workspace.cursorPos` | no focus theft, reliable center on Wayland (S2) |
| next | Esc cancel in the radial menu: to be decided between temporary global Esc shortcut and exclusive keyboard | `none` receives no key events (S2) |

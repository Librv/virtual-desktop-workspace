# T2 findings

Date: 2026-10-17. Nested session `VDW_DEV_DIR=/run/user/1000/vdw-t2`, KWin 6.7.5.

## KWin script ids collide: use `Scripting.start()`, not `Script<id>.run`

`org.kde.kwin.Scripting.loadScript` returns an id that is the number of
scripts currently loaded. After an unload from the middle, a new script gets
the id of one that is still loaded (load A=0, B=1, unload A, load C returns 1).
The object path `/Scripting/Script1` then belongs to B, so calling `run` on it
never starts C. This hit vdwd as soon as a query script was loaded and
unloaded around the long-lived placer: the placer silently never ran.

Fix used in `src/daemon/kwinscripts.cpp` and the integration test: after
`loadScript`, call `Scripting.start()`, which runs every loaded script that is
not running yet (verified: C starts). `unloadScript(name)` is by name and
unaffected. The S3 spike used `Script<id>.run`; the S3 and ARCHITECTURE text
("`loadScript` then `run`") should say `start` instead.

## Kate `--new`

With a Kate window open: `kate -b /tmp/f` handed the file to the running
instance and opened no window (as in S4); `kate -b --new /tmp/f` opened a new
window. So a slot can use `Args=--new` with `App=org.kde.kate`; no code change
needed.

## Other

- Qt log output of vdwd goes to the journal when stderr is not a tty; run with
  `QT_FORCE_STDERR_LOGGING=1` to see `vdw.daemon` lines in a terminal or test.
- `OpenWorkspace` also replies `busy` (unless forced) while launches of an
  earlier open are still pending, because the desktop looks empty until their
  windows appear.
- Apps with `DBusActivatable=true` are activated over D-Bus: slot `Args` are
  ignored and the job pid is 0, so matching falls back to the app id.

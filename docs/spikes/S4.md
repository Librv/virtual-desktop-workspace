# S4 findings: launching apps and matching windows

Date: 2026-10-17. KWin 6.7.5, KF6 6.31, Konsole/Dolphin/Kate 26.08.2. All runs
in a private nested session (`VDW_DEV_DIR=/run/user/1000/vdw-s4`), Wayland
only (Xwayland was up but unused). Firefox is not installed: not tested.

Code: `spikes/S4/` (throwaway). `s4launch.cpp` launches `ID[=ARGS]...` via
`KIO::ApplicationLauncherJob` (extra args appended to the service `Exec`),
`watch.js` logs `windowAdded` with pid, resourceClass, desktopFileName,
caption, `dump-props.js` prints every property KWin exposes on a window,
`run-case.sh` runs both side by side and merges the output by timestamp.

## Summary

- `ApplicationLauncherJob` returns the pid of the process it spawned
  (`job->pid()`, one pid per launch). It is the pid of the app only when the
  app does not fork or forward. For the apps below it is the window's pid
  except when the app forwards to an already running process (Konsole in
  single-process mode, Kate with an existing instance).
- `desktopFileName` of every new window equals the `.desktop` id
  (`org.kde.konsole`, `org.kde.dolphin`, `org.kde.kate`), and so does
  `resourceClass`. Both are set on the `windowAdded` signal already (no
  `desktopFileNameChanged` was ever seen afterwards).
- Matching by pid alone is exact for Dolphin and normal Konsole and Kate, and
  impossible for single-process Konsole. Matching by app id alone (FCFS) is
  wrong as soon as an unrelated window of the same app appears between two
  launches (observed). Combine: pid first, app id FCFS as fallback.
- An XDG activation token can be passed with `setStartupId()` and reaches the
  app (`XDG_ACTIVATION_TOKEN` in its environment), but it is NOT exposed by
  the KWin scripting window API. It cannot make script-side matching exact.

## Q1: which pid does ApplicationLauncherJob give back?

`job->pid()` / `job->pids()` returned exactly one pid per launch, available
as soon as `result` fires (about 1 ms after `start()`), error=0 always. It is
the pid of the process KIO spawned (`konsole`, `dolphin`, `kate -b`). Each
spawned process is in its own systemd scope (`app-org.kde.konsole-N.scope`
under `app.slice`) when systemd is available; that is how KIO starts them.
Extra args work by editing the `Exec` of a `KService` copy
(`service->setExec(exec + " " + args)`), e.g. `konsole --workdir /tmp`,
`dolphin %u /tmp`, `kate -b %U /tmp/a.txt`. The field codes (`%u`, `%U`)
stay in the string and are removed by KIO; the extra argument ends up as the
argument. Note: a plain `QStringList` of URLs via `setUrls()` is the
supported way to pass files; for generic flags like `--workdir` appending
to `Exec` is needed (no API for extra args on the job).

Gotcha for the spike tool (not for the daemon): `KJob` holds a
`QEventLoopLocker`, so a GUI app without windows quits when its first job ends
unless `QCoreApplication::setQuitLockEnabled(false)`. The daemon will have
its own lifecycle but should be aware.

## Q2/Q3: per app observations (all times relative, ms)

Launched pid vs window pid, class and desktopFileName, as seen by
`windowAdded` in a KWin script. "launch" = pid from the job.

### Konsole, normal (one process per window)

3 launched at once (`konsole`, `--workdir /tmp`, `--workdir /usr`):

| launch | job pid | window pid | class | desktopFileName | window at |
|---|---|---|---|---|---|
| 0 | 133361 | 133361 | org.kde.konsole | org.kde.konsole | +105 |
| 1 | 133362 | 133362 | org.kde.konsole | org.kde.konsole | +105 |
| 2 | 133363 | 133363 | org.kde.konsole | org.kde.konsole | +108 |

Window order differs from launch order (1, 0, 2 here): FCFS by app id would
swap placements. Pid matches exactly.

Unrelated Konsole opened by "the user" between launch 0 and launch 1
(launches 300 ms apart):

| event | pid | caption |
|---|---|---|
| launch 0 | 67618 | window pid 67618 (+200) |
| unrelated konsole | 67622 | "var : zsh" window at +203, BEFORE launch 1 was even started |
| launch 1 | 67660 | window pid 67660 |
| launch 2 | 67673 | window pid 67673 |

FCFS by app id would give the unrelated window to launch 1. Pid matching is
correct.

### Konsole, "Run all Konsole windows in a single process"

Set as `[KonsoleWindow] UseSingleInstance=true` in the NESTED session's
`konsolerc` only. (Found in `libkonsoleapp` strings, key `UseSingleInstance`.)

3 at once, cold (no Konsole running):

| launch | job pid | window pid | class | desktopFileName |
|---|---|---|---|---|
| 0 | 134195 | 134196 | org.kde.konsole | org.kde.konsole |
| 1 | 134196 | 134196 | org.kde.konsole | org.kde.konsole |
| 2 | 134197 | 134196 | org.kde.konsole | org.kde.konsole |

All windows belong to one process (the one that won the startup race, here
launch 1). The other launched processes forward over D-Bus and exit. Job pids
are useless for matching here, except that the window pid equals ONE of them
(not reliable to depend on). With the process warm, all three launches' pids
differ from the window pid (134196).

Timing detail: one window was created per launch, 24 to 88 ms apart; two
windows initially had the caption "Built-in - Konsole" and became
"agent... : zsh" / "usr : zsh" after `captionChanged` about 12 ms later.
The caption is therefore not stable at `windowAdded` time: never match on
it.

Unrelated Konsole between launches in single mode: it also becomes a window
of the same process (same pid, same class) so only order distinguishes it:
the "var" window arrived between window 0 and window 1. With FCFS it would
take launch 1's slot.

### Dolphin

One process per window (no reuse), all launches independent.

| case | job pid | window pid | class / desktopFileName |
|---|---|---|---|
| single | 137285 | 137285 | org.kde.dolphin / org.kde.dolphin |
| 3 at once (warm) | 70148, 70149, 70150 | same | same |
| 3 launched 500 ms apart | 69376, 69392, 69456 | same | same |
| launched while another is open | 69066 | 69066 | same |

Window order again differed from launch order when launched at once
(usr, Home, tmp). Cold start in a brand new profile was slow: the first
Dolphin windows appeared 25.5 s after launch (the 3-at-once run, and the
single launch right after was fast, so this looks like a one-time D-Bus
timeout during first-run setup, not a Dolphin property). Warm start is
about 120 ms.

### Kate (`kate -b %U`)

| case | job pid | window pid | class / desktopFileName |
|---|---|---|---|
| 3 at once, cold (no file, a.txt, b.txt) | 68329, 68330, 68331 | 68329, 68330, 68331 | org.kde.kate / org.kde.kate |
| 2 launches (no file, c.txt) with Kates already open | 68630, 68631 | only 68630 got a window | same |

With other Kate instances running, opening a file went into an existing
instance and NO new window appeared (launch 1 never produced a window). So
a launch may produce zero windows: pending placements need a timeout and
must not be assumed to complete. Kate honours `-n`/`--new` style options for
a separate window; the `.desktop` file only has `-b`.

## Q4: activation or startup token

- `KIO::ApplicationLauncherJob::setStartupId(QByteArray)` sets the token. In
  the nested session a token requested with `KWaylandExtras::xdgActivationToken()`
  returned `kwin-12`, `kwin-13`, ... (one per request), without needing a
  window of ours (`nullptr` window with a serial of 0 worked).
- The token reaches the app: `/proc/<pid>/environ` of the launched Kate and
  Dolphin contains `XDG_ACTIVATION_TOKEN=kwin-44` / `kwin-45`. Without
  `setStartupId()` (headless, no window of ours) nothing is set.
- It is NOT visible to KWin scripts. `dump-props.js` lists every window
  property in 6.7.5: no startup id, token or activation field (closest:
  `pid`, `resourceName`, `resourceClass`, `desktopFileName`, `tag`,
  `description`, `internalId`). So a script cannot ask "which token did this
  window come from". KWin uses the token internally to place or activate the
  window on the right desktop but does not expose the mapping.
- `tag` and `description` (xdg-toplevel-tag, 6.22+) are set by the CLIENT, so
  we cannot inject them from outside.

What the token CAN do (unverified here): when the daemon hands KWin a token
for the app id, KWin may place the new window on the desktop it was
requested from. Not needed since we place windows explicitly.

## Recommended matching strategy

Per launched app the daemon records a pending entry:
`{launchId, appId (desktop id), jobPid, startTime, slot}`.

On each `windowAdded(window)` (normal windows only, `normalWindow &&
!transient`), in the script or the daemon:

1. Exact: if `window.pid == jobPid` of a pending entry, claim that entry.
   Verified exact for normal Konsole, Dolphin, Kate.
2. Fallback: else match the oldest pending entry whose `appId` equals
   `window.desktopFileName` (fall back to `resourceClass` when
   `desktopFileName` is empty) and whose pid is "shared": the job pid is not
   alive as the window's process, or the window's pid equals a pid already
   attributed to another entry (single-process apps). Oldest first (launch
   order). Needed for single-process Konsole.
3. A window that matches nothing is left alone.

Why not only FCFS: observed counter-example (unrelated Konsole opened between
two launches, and window order differing from launch order when launched at
once). Why not only pid: single-process Konsole.

Residual risk, accepted: in single-process apps an unrelated window of the
same app opening during setup can steal the oldest pending slot. It is
unavoidable without a token visible to scripts. Reduce it by launching with a
small gap and by detecting "pid already known to belong to a live process we
did not start" (not needed for v1).

Order and timing for single-process apps: windows arrive in launch order
only by luck (observed order differed). Do not rely on order for pid-shared
entries beyond FCFS; the placement of identical apps (3 Konsoles) is
interchangeable by definition, so a swap is harmless when they are launched
with the same args. When args differ (`--workdir`), the caption ends up
carrying the workdir ("tmp : zsh") but only after `captionChanged`, so it
cannot be used reliably.

Launching in sequence (e.g. 150 to 300 ms apart) instead of all at once makes
FCFS closer to launch order and costs little; the spike did not need it for
the pid path.

### Timeouts (proposal)

- Per pending entry: 10 s warm. First start of an app in a fresh profile took
  25 s (Dolphin). Use 10 s by default, and make it configurable; on timeout
  drop the entry and carry on (a launch may legitimately open no window, e.g.
  Kate forwarding a file to a running instance).
- Whole workspace: finish when every entry is claimed or timed out. Do not
  block a second workspace on it beyond that.
- Observed warm latency launch to `windowAdded`: Konsole 100 to 200 ms,
  Dolphin 120 ms, Kate 150 to 450 ms.
- Window geometry: apply on `windowAdded` straight away. In single-process
  Konsole the caption changes later but class, pid and desktopFileName are
  already final.

## Recommendations for T2

- Use `KIO::ApplicationLauncherJob` with a `KService` copy and appended
  args; read `job->pid()` in the `result` handler. Call
  `setQuitLockEnabled(false)` or hold a QEventLoopLocker only if the daemon
  has no window.
- Keep the matching in a pure, unit-testable class (`PendingPlacements`):
  input = launches and observed windows `{pid, appId, time}`, output =
  assignment. Implement the two-step strategy above.
- Prefer doing the claim in the daemon (the script just reports every
  `windowAdded` with pid, desktopFileName, resourceClass, internalId) and
  have the script apply geometry for an `internalId` the daemon names.
- Do not match on caption. Do not rely on the activation token for matching.
- Pending entries must expire; an app that opens no window is normal.

## Proposed ARCHITECTURE/DECISIONS changes

- ARCHITECTURE "Matching windows to launches": replace "keyed by the app id"
  with "pid first (job pid equals window pid), then app id FCFS in launch
  order for apps that share a process; entries expire after 10 s (configurable)".
  Note that activation tokens are not visible to KWin scripts.
- DECISIONS: "Window matching: pid first, then desktopFileName FCFS, expiry
  10 s; no reliance on activation tokens (not exposed by KWin scripting)".

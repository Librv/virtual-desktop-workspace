# S1 findings: KGlobalAccel tap, hold, confirm

Date: 2026-10-17. KWin 6.7.5, KF6 6.31, Qt 6.12, nested session from T0b.

## Summary

| Question | Answer |
|---|---|
| 1. What does `globalShortcutActiveChanged` report? | One `active=true` on the first press, one `active=false` on release of the last key (D). Auto-repeat does NOT produce more `active` changes, only `QAction::triggered`. A second tap of D with Ctrl+Meta held gives a clean second true/false pair. Verified in the nested session with real injected key events. |
| 2. Can modifier release be detected on Wayland? | Yes. `KModifierKeyInfo::keyPressed(Qt::Key, bool)` reports Control and Meta press and release (backed by KWin's `org_kde_kwin_keystate` v5, state "pressed"). Verified in the nested session. So confirm CAN strictly require held modifiers. The timeout is still needed as the upper bound. |
| 3. Editable in System Settings, Shortcuts? | Component and action are registered with the right names and friendly names, and an edit made through the kglobalaccel D-Bus API (the same call the KCM makes) takes effect immediately, is persisted, and is reported back via `globalShortcutChanged`. The KCM window itself was not looked at (see "Not verified"). |
| 4. Works in the nested session? | Yes, fully, once key events are injected with `org_kde_kwin_fake_input` from a small client authorized by a `.desktop` file in the nested XDG_DATA_HOME. |

## Method

Throwaway code in `spikes/S1/`:

- `s1probe.cpp`: registers an action through `KGlobalAccel` (component
  `vdw-s1-probe`, action `vdw-s1-main`, default Ctrl+Meta+D) and prints a
  timestamped line for every `globalShortcutActiveChanged`, `QAction::triggered`
  (QAction auto-repeat is on by default, see Q1),
  `globalShortcutChanged` and `KModifierKeyInfo::keyPressed`.
- `s1inject.cpp`: sends key press and release through `org_kde_kwin_fake_input`.
  Steps: `+ctrl`, `-d`, or a number of milliseconds to wait.

Build and run (nested session only):

```
cmake -S spikes/S1 -B spikes/S1/build -G Ninja && cmake --build spikes/S1/build
export VDW_DEV_DIR=/run/user/1000/vdw-s1
scripts/dev-session.sh start --no-xwayland
scripts/dev-session.sh run -- spikes/S1/build/s1probe --seconds 600 &
scripts/dev-session.sh run -- spikes/S1/build/s1inject +ctrl 30 +meta 30 +d 80 -d 30 -meta 30 -ctrl 300
scripts/dev-session.sh stop
```

### Key injection in the nested session: works

KWin only hands `org_kde_kwin_fake_input` to authorized clients
(`src/wayland_server.cpp`, `KWinDisplay::allowInterface`; the interface is on a
blacklist). A client is authorized when the `.desktop` file that owns its
executable path lists the interface in `X-KDE-Wayland-Interfaces`
(`KWIN_WAYLAND_NO_PERMISSION_CHECKS=1` would also disable the check, not needed).

Without the file, the client was refused:

```
inject       0 error: org_kde_kwin_fake_input not announced to this client (not authorized?)
```

With this file in the nested `$XDG_DATA_HOME/applications/` (that is
`$VDW_DEV_DIR/home/.local/share/applications/vdw-s1-inject.desktop`, never the
real `~/.local`):

```
[Desktop Entry]
Type=Application
Name=VDW S1 fake input injector
Exec=<absolute path of spikes/S1/build/s1inject>
NoDisplay=true
X-KDE-Wayland-Interfaces=org_kde_kwin_fake_input
```

the protocol is announced (`name=59 version=6`) and the keys reach KWin's
shortcut handling, and also `KModifierKeyInfo`. Injection goes to the nested
KWin only (the client talks to the nested `WAYLAND_DISPLAY`). Note the
authorization is per executable path, so the file has to be rewritten if the
build directory moves. T3's integration tests can reuse this approach.

## Q1: what `globalShortcutActiveChanged` reports

Times are ms since probe start (left column) with the injector's own steps
described in the header of each case. `mod` lines come from `KModifierKeyInfo`.

**Quick tap** (ctrl, meta down, D held 80 ms, then all released):

```
  6151 mod Control 1
  6181 mod Meta 1
  6211 active=1
  6211 triggered
  6291 active=0
  6321 mod Meta 0
  6351 mod Control 0
```

**Long hold** (D held 1500 ms, key auto-repeat at 25 Hz after about 600 ms):

```
 12052 mod Control 1
 12082 mod Meta 1
 12112 active=1
 12112 triggered
 12725 triggered        <- first auto-repeat, ~610 ms after press
 12767 triggered        <- then every ~40 ms, 25 repeats in total
 ...
 13607 triggered
 13614 active=0
 13644 mod Meta 0
 13674 mod Control 0
```

So: exactly one `active=true`, no `active` events for repeats, one
`active=false` at D release. Auto-repeat only shows as `QAction::triggered`
(and only because QAction auto-repeat defaults to true: in
`KGlobalAccelPrivate::invokeAction` a Repeated event is dropped when
`!action->autoRepeat()`). The daemon should therefore set
`action->setAutoRepeat(false)` and use only `globalShortcutActiveChanged`, or
ignore `triggered` altogether. Source: `kglobalacceld` `GlobalShortcutsRegistry`
emits Pressed/Repeated/Released per key event, and `KGlobalAccel` emits
`globalShortcutActiveChanged(true)` only when the action is not already the
`m_lastActivatedAction`.

**Tap, then a second tap of D 500 ms later, Ctrl+Meta held throughout:**

```
 25767 mod Meta 1
 25797 active=1
 25797 triggered
 25877 active=0
 26378 active=1
 26378 triggered
 26458 active=0
 26488 mod Meta 0
 26518 mod Control 0
```

A clean second pair. Modifiers do not need to be re-pressed, and nothing is
swallowed.

**Menu then confirm** (hold D 800 ms, release D with modifiers held, tap D
again, release everything):

```
 49379 active=1     (menu opens after 250 ms by timer in the daemon)
 50179 active=0     (D released: menu selection)
 50780 active=1     (confirm tap)
 50860 active=0
 50890 mod Control 0
 50920 mod Meta 0
```

**Ctrl released while D is still held:** `mod Control 0` and `active=0` arrive
in the same millisecond (kglobalacceld releases the shortcut when a modifier of
it is released, because the Released event comes from the first key that goes
up and is matched via `m_lastShortcut`). So for the radial menu the shortcut
"release" fires when ANY of Ctrl, Meta, D goes up, not just D:

```
 36840 active=1
 37140 mod Control 0
 37140 active=0
 38170 mod Meta 0
```

**A Meta-only shortcut** (what Plasma's launcher uses) registered in a second
probe did not fire at all during any Ctrl+Meta+D gesture (only for a bare Meta
tap), so there is no interference with the launcher.

### Pitfall: `invokeShortcut` over D-Bus

`org.kde.kglobalaccel.Component.invokeShortcut` sends a Pressed without a
Released. `KGlobalAccel` then thinks the action is still the
`m_lastActivatedAction`, so the NEXT real press produces `triggered` but no
`active=1` event:

```
  2022 active=1 / triggered     <- invokeShortcut
  2868 mod Control 1 ...
  2928 triggered                 <- real tap: no active=1 !
  3008 active=0
  3982 active=1                 <- the next tap is normal again
```

This only matters for tests or tools that call `invokeShortcut` (do not use it
for the debug inject interface). It also means a state machine must tolerate
an `active=0` that was not preceded by `active=1`, and should reset on it.

## Q2: modifier release on Wayland

Candidates tried or read:

| Approach | Result |
|---|---|
| `KModifierKeyInfo` (KGuiAddons) | Works. On Wayland it wraps `org_kde_kwin_keystate` v5, which KWin sends on every `Xkb::modifierStateChanged`. Reports `keyPressed(Qt::Key_Control, bool)` and Meta, Shift, Alt, AltGr. Latency about 0 to 30 ms after the injected key in the tests above. `keystate` is not on KWin's permission blacklist, so a normal app can bind it. Verified in the nested session (all `mod` lines above). |
| `QGuiApplication::queryKeyboardModifiers()` | Not useful: on Wayland it reflects only the focused surface's state, and the daemon has no focus. Not tried live. |
| KWin script | Possible in principle, but KWin scripts have no raw key or modifier API (`shortcuthandler.h` only offers activated shortcuts). Not needed. |
| Separate global shortcut for the modifier | Not needed. |
| `libinput`/evdev | Rejected: needs input group, bypasses the compositor. |

Caveat: `keystate` tells the state of the modifiers as seen by KWin's XKB
state, which is exactly what we want. The initial state is fetched with
`fetchStates` and then pushed (`KModifierKeyInfo` does both).

Conclusion: confirm CAN strictly require that Ctrl and Meta are still down.
It also works as the cancel signal: when either goes up the pending confirm
can be dropped immediately, with the 2 s timeout as a safety net (for example
if KWin or the daemon restarts, or the keystate event is missed).

## Q3: System Settings, Shortcuts

Observed through the kglobalaccel D-Bus API in the nested session (the same API
the KCM uses):

- `allComponents` lists `/component/vdw_s1_probe`; `friendlyName` is
  "VDW S1 probe". The action is listed with friendly name "S1 probe: main
  gesture" and the key `335544388` (Meta+Ctrl+D) as both current and default.
- `setForeignShortcut` (the KCM's edit call) to Meta+Ctrl+E: the probe got
  `globalShortcutChanged Meta+Ctrl+E`, the old chord Ctrl+Meta+D then
  produced no `active` event (the new chord was not injected), and the nested `kglobalshortcutsrc` stored
  `vdw-s1-main=Meta+Ctrl+E,Meta+Ctrl+D,S1 probe: main gesture`
  (current, default, name).
- Restart persistence: with `KGlobalAccel::Autoloading` (setShortcut flag) a
  restarted probe got the user key (`Meta+Ctrl+E`); with `NoAutoloading` it
  overwrote the user's edit with the default again (`Meta+Ctrl+D`). The real
  daemon must use Autoloading and set the default with `setDefaultShortcut`.
- Removing: `KGlobalAccel::removeAllShortcuts(action)` removed the component's
  group from `kglobalshortcutsrc` shortly after exit. A real daemon should
  NOT do this on exit (it would lose the user's key); it should only call it
  when a workspace is deleted.
- Component name and display name are taken from the `componentName` and
  `componentDisplayName` properties on the QAction; without them kglobalaccel
  uses the application name. For a daemon with many actions (main plus
  per-workspace shortcuts) all actions should share one component (say
  "vdw") with one friendly name.

Two things a daemon needs for the KCM to show the shortcut: it must register
the action at least once (the component appears after the first
`setShortcut`/`setDefaultShortcut`), and the QAction must have a non-empty
object name (it is the unique id) and text (the label).

## Not verified

- The System Settings Shortcuts page itself was not looked at: the attempt to
  screenshot `kcmshell6 kcm_keys` in the nested session was cut off when the
  session was stopped, and was not redone. Answer 3 above rests on the D-Bus
  API plus kglobalshortcutsrc. The user should look at it (live steps).
- Real keyboard on the live session: scancode-level behavior, user repeat
  settings, and whether other software (an input method, a remapper such as
  keyd or kmonad, a game, remote desktop) alters the press/release sequence.
- Keyboard layouts where D is not at the US position: kglobalaccel matches on
  the keysym; layout switching was not tried.
- Key chords where Ctrl+Meta+D is already taken (conflict dialog behavior).
- Behavior when a window inhibits shortcuts (`isKeyboardShortcutsInhibited`,
  e.g. a VM or remote desktop client in focus): from the KWin source
  (`input.cpp`, `GlobalShortcutFilter::keyboardKey`), no event is sent to
  kglobalacceld then, press and release both. A release is not synthesized
  when focus moves to such a window while the shortcut is held (not tested),
  so the state machine's timers must also cover this.
- Release when the radial menu (S2) takes keyboard focus: that is S2's
  question; kglobalacceld sees key events only while KWin passes them to
  `GlobalShortcutFilter`, which runs before the focused client.

## Steps for the user on the live session

Run from the repo root in a terminal on the live session (the probe removes
its own shortcut on exit; it uses its own component `vdw-s1-probe`, and the
test key Ctrl+Meta+D collides with the legacy `setup-workspace.sh` shortcut if
that is bound there, so use a different key if it is):

1. `cmake -S spikes/S1 -B spikes/S1/build -G Ninja && cmake --build spikes/S1/build`
2. `spikes/S1/build/s1probe --seconds 120 --shortcut "Ctrl+Meta+F9"`
   (any free chord with Ctrl+Meta+key works; plain Ctrl+Meta+D also works if
   the legacy script is not bound.) This only registers one shortcut and logs;
   it does not move or launch anything.
3. In another terminal watch nothing: the output appears in the first one.
   Do each and paste the log: (a) tap the chord; (b) hold it for 2 s;
   (c) tap, then tap the last key again while still holding Ctrl+Meta;
   (d) hold the chord, release only Ctrl, then the rest; (e) hold and release
   only the last key while keeping Ctrl+Meta down.
4. Open System Settings, Shortcuts, find "vdw-s1-probe" (type it in the
   search box, or look under the Add Application / custom list: it appears as
   "VDW S1 probe" while the probe runs), change the key, confirm that the
   probe prints `globalShortcutChanged` and that the new key works.
5. Check that a Meta-only press (launcher) is not disturbed by the probe.
6. Stop the probe with Ctrl+C. In System Settings the entry should be gone
   after a refresh.

## Recommendation for T3

1. Register ONE QAction per shortcut under one component ("vdw"), with
   `setAutoRepeat(false)`, `setDefaultShortcut(..., NoAutoloading)` for the
   default and `setShortcut(..., Autoloading)` so user edits in System
   Settings survive restarts. React to `globalShortcutChanged` only for UI.
2. Drive the state machine from `globalShortcutActiveChanged` only:
   `true` is Press, `false` is Release. Ignore `triggered`.
3. Subscribe to `KModifierKeyInfo::keyPressed` for Control and Meta (and
   Shift/Alt only if they are part of the configured sequence: derive the set
   from the QKeySequence, do not hard code), and expose the combined state as
   an input `modifiersHeld(bool)` to the state machine. Keep this layer thin
   so the machine stays pure: inputs `press`, `release`, `modifiersChanged`,
   `timer`, `menuSelection`.
4. States and rules:
   - idle: press starts the hold timer (250 ms). State pressed.
   - pressed: release before the timer is a tap: open default workspace (or
     start confirm if busy). Timer fires: open the radial menu, state menu.
   - menu: release (of the shortcut) means selection (center = cancel).
     Because the release fires when ANY of the chord's keys goes up,
     releasing Ctrl first is equivalent to releasing D: fine for the menu.
   - awaiting confirm: started with a 2 s timer (configurable) when the OSD is
     shown. A `press` while `modifiersHeld` is true confirms. The timer
     firing, `modifiersHeld` going false, or Esc cancels.
   - Confirm after a menu pick: the menu pick happens on release, at which
     point the user may already have released the modifiers. The spec says
     "tap D again (while holding Ctrl+Meta)". If the user releases Ctrl+Meta
     together with D at the end of the pick (the common case), strict mode
     cancels the confirm immediately, which makes the confirm flow
     unreachable. Therefore: for the menu path, start the confirm window
     with a grace rule: modifiers going up while the machine entered confirm
     less than about 300 ms ago, or not yet seen as held, do not cancel;
     the confirm is then valid until the timeout, and a new press of the
     shortcut (which by definition re-presses Ctrl+Meta) confirms. In other
     words: "modifiers released" only cancels if they were held when the
     confirm began and are released after that and no press has happened.
     If this is too complicated, the simplest correct rule is: a `press`
     of the shortcut during awaiting confirm always confirms (the press
     itself implies the modifiers are held at that moment), and
     `modifiersHeld` releasing is used only to cancel in the TAP path.
     That is what I recommend for T3.
5. Strict modifier-held is therefore achievable but is not needed to confirm:
   a fresh press of Ctrl+Meta+D already implies the chord is held at the
   press instant. Requiring the modifiers to stay held through the 2 s window
   only changes behavior when the user lets go and presses the chord again
   (the "press chord again within 2 s" case in the test above, which also
   produced a clean `active=1`). Recommendation: allow that (it matches the
   timeout rule of decision 2), cancel early on modifier release in the tap
   path only if user testing shows the OSD feels sticky.
6. Debug inject interface: have it call the state machine directly, do not
   go through `invokeShortcut` (leaves kglobalaccel's `m_lastActivatedAction`
   set and swallows the next real `active=1`).
7. State machine must tolerate: `release` without `press` (after
   `invokeShortcut`, or when kglobalacceld restarts, which releases the
   shortcut), a second `press` without a `release` in between (reset to
   pressed), and a timer firing after reset (use generation counters or
   restart timers).
8. Tests: unit tests with an injected clock for every transition above, and
   an integration test with `s1inject` plus the nested session (needs the
   `.desktop` authorization file, see Method). The injection tool can be
   promoted from `spikes/S1/` into `tests/` as is.

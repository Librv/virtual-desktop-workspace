# T8: Browser profiles for each slot (Helium)

**Depends on:** T7. **Branch:** `worktree-feat-browser-profile`, one PR for
all milestones. Decisions: DECISIONS 34 to 42.

A slot of a known browser can name a Chromium profile (`Profile=` in vdwrc).
vdwd opens the browser in that profile.

## Milestones

- **M1, profile key and launch:** `Slot::profile`, config read and write,
  browser table, `Local State` parser, launch args in vdwd. A missing profile
  launches the last-used profile and logs a warning.
- **M2, repeated browser slots:** a workspace can have more than one slot of
  the same browser, with or without a profile. vdwd launches those slots one
  at a time (DECISIONS 41, 42). The next slot starts when the matcher claims
  the window of the previous slot, when its pending entry expires, or when its
  launch fails.
- **M3, missing-profile notification:** vdwd sends a KNotification that names
  the app and the profile, in place of the M1 warning (the log line stays).
  It covers both cases (missing profile, unreadable profile list), with one
  notification for each slot.
- **M4, profile picker in the KCM:** a "Profile" combo box for browser slots,
  with "Last used" and the display names from `Local State`.

## Acceptance

- `Profile=Profile 1` in a Helium slot opens Helium in that profile.
- A missing profile opens the last-used profile, with a warning (M1) and a
  notification (M3).
- Config without `Profile` writes the same bytes as before. Config with
  `Profile` reads back the same.
- Two Helium slots with different profiles always go to their own slots (M2).
- The user can select a profile in the KCM and save it (M4).
